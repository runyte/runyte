## Linux Node registration

`test_actual_publication_deadline_leaves_host_headroom_and_ignores_late_success`
failed in `opened()` -> `handshake()` -> `read(phase='registration')`, before
invoking a command or starting the publication timer. The diagnostic reports
3.003 seconds elapsed, a still-running child, zero partial bytes, zero queued
messages and empty stderr. The other thirteen Node cases passed.

`docs/plugins/check_node.py` starts a fresh Node process and sends hello without
a separate startup barrier. Its ordinary three-second response deadline also
covers interpreter startup and module loading. The real host instead starts a
ten-second registration deadline in `src/plugin/worker.rs::run`, using
`src/plugin/boundary.rs::TIMEOUT`. The fixture's tighter startup assumption is
not the publication contract being tested. The publication case separately
checks the example's eight-second request deadline within a nine-second bound.

The buffered-message defect fixed by `aadaf48` cannot explain the recorded
empty reader queue. The diagnostics do not establish whether Node was delayed
in startup, scheduling or input handling. Cold startup is a hypothesis, not a
proven operating-system diagnosis. The existing
[resolution](../issues/resolved/node_conformance_readiness.md) explicitly
retains this unknown cause.

Implemented correction and validation:

- Registration has its own absolute budget aligned with the host's ten-second
  registration allowance, measured from child launch. Release-boundary and
  malformed-initial-input cases use the same startup allowance. Ordinary
  post-registration replies and the publication-deadline assertion are unchanged.
- The harness records the resolved Node executable/version and
  launch-to-registration timing.
  The job installs distribution Node, but the harness resolves `NODE` or `PATH`;
  the package-install log alone does not prove which executable ran.
- Bounded failure diagnostics remain. If a child still misses the host-aligned
  deadline, capture startup/readiness stage evidence in a diagnostic run before
  claiming an interpreter or protocol fix. Do not hide failures with reruns or
  an unconditional warm-up.
- Four additional deterministic tests cover delayed initial registration,
  permanent silence, EOF and fragmented
  responses while preserving one absolute deadline, including late descriptor
  readiness. The real-process suite continues checking the
  eight-second publication timeout and rejection of late success.

Local evidence on Linux with `/usr/bin/node` v22.22.2: twenty fresh-process
registrations completed in 0.061–0.093 seconds. The six reader cases and fourteen
real Node cases passed during the preceding review. All ten reader cases and
fourteen Node cases passed after implementation. These results do not
reproduce or explain the CI delay, nor prove a larger startup budget fixes it.

## Windows replacement publication

`native_manager_visits_selected_live_publication_and_refuses_stale_row` failed
inside its `public_manager_visit_fixture` subprocess. At
`tests/windows_public_attachment.rs:788`, `start_visit_host` reported:
`replacement host failed: Error: workspace publication lock is busy`.

The earlier successful visit had already completed. For the stale-row case,
the fixture stops the destination host, waits for its process to exit, and
starts a replacement while the source session manager remains open. The
replacement exits before reaching publication readiness; the intended
stale-selection refusal has not yet been exercised.

`src/workspace/windows_endpoint/locking.rs::Lock::acquire` uses exclusive
`LockFileEx` with `LOCKFILE_FAIL_IMMEDIATELY`. Every lock managed by that helper
reports the same publication-lock message, including the name-store lock.
`src/windows_host.rs` propagates a preparation error directly out of startup.

A concrete contention path exists without a surviving old host:

- Catalog reads of stopped sessions call `NameStore::read_existing`, which
  acquires the stable name-store lock even when no name record exists.
- `EndpointLocation::finish_named_preparation` requires that same lock while
  preparing the replacement publication.
- The source manager's catalog reads and the fixture's `--session-list`
  readiness probes can overlap replacement startup. If a reader holds the lock,
  startup receives `WouldBlock` and exits immediately.

This path is established by source inspection. The CI message does not identify
the exact contended lock or owning process, and native reproduction was not
available in the Linux review environment. It should not be dismissed as a
test-only timing failure: public startup uses the same preparation path.

Implemented correction and required native validation:

- `EndpointLocation::prepare_named_until` handles typed preparation-lock
  contention with
  one bounded, cancellable deadline coordinated with the existing five-second
  detached readiness budget. The host starts this deadline on entry and selects
  preparation against termination and foreground-parent exit. It retains the
  project lease and releases all partial identity/registry/name guards before
  waiting 25 milliseconds, then revalidates and reacquires the complete
  preparation. Synchronous filesystem work stays on the startup owner.
  Publication after preparation is attempted once.
- Immediate failures remain for invalid identity, permissions, occupied
  publications and conflicting project ownership. The low-level try-lock
  contract remains unchanged.
- Lock errors now carry role context so a recurrence distinguishes identity,
  registry and name-store contention without guessing.
- Five native tests were added. One deliberately holds the stopped-name read
  lock while
  replacement startup attempts preparation, then releases it and requires
  successful publication. Others cover permanent contention, cancellation,
  release of partial guards, rejection of competing project ownership,
  and revalidation of vacancy and project identity. The public stale-row test
  and its exact-publication assertion are unchanged. These tests still require
  native execution; Linux excludes this module with `cfg(windows)`.

The separate required restart/save, context-bridge and clipboard steps passed.
Native language-server provisioning and acceptance were skipped after the
ordinary-suite failure, so this run provides no acceptance result for them.
